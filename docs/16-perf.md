## 一、本章目标

阶段 1~9 把功能形态补齐之后，阶段 10 回到 roadmap 的性能初心：
**用数字说话**。本章交付四件事：

1. **分位数草图**（HdrHistogram 思想的从零实现）——百万样本下的
   O(1) 内存、O(1) 记录、任意分位数查询；
2. **conn-storm**（M1 里程碑：单机 10 万并发连接）——真实 TCP 三次
   握手 + 真实握手帧走完整服务端路径，含每连接内存账本；
3. **weak-link**（可靠性里程碑）——用户态弱网模拟器（帧级丢包/延迟/
   乱序注入，确定性可复现）+ 真实双端的重传到达率实测；
4. **一场真实的缺陷发现**：weak-link 抓出接收窗**静默楔死**缺陷
   （双向 10% 丢包下到达率只有 29.5%），定位、修复、回归、复测全程
   闭环——这是本项目第一次「压测发现生产缺陷」，也是本章最有
   价值的部分。

三级里程碑的诚实账本（本机：Windows 11 · 16 逻辑核 · release 构建）：

| M2 单机 100 万连接 | 1,000,000 | 未开始——需要 `io_uring` / 内核调优 / 每连接 KB 级内存，是 Linux 平台的工作 | 未开始 |

## 二、概念：压测方法学（Java 对照）

### 2.1 观察者效应与分位数草图

压测工具自己也在消耗被测系统的资源：阶段 7 的 group-fanout 用
「采样 → 排序 → 最近邻分位数」——30 个样本毫无问题；阶段 10 的
测量对象是**百万级样本**（弱网链路的逐消息延迟、连接风暴的逐连接
计时），排序数组的内存 O(n) 与查询 O(n log n) 会让**测量工具变成
被测系统的竞争者**——这就是压测版的观察者效应。

解法是**分位数草图**（quantile sketch）：用精度换资源。Java 工程师
对照 `HdrHistogram`（Gil Tene 著名库，JMH 生态的标配）——对数分桶 +
桶内线性细分，任何值的记录误差相对值有界。本章 `histogram.rs` 从零
实现了它的骨架（114KB 固定内存、O(1) 记录、相对误差 ≤ 0.39%），
推导与对照见 §三。

### 2.2 可重现的随机：确定性丢包模型

真实链路最难的三个字是「可重现」：公网上做丢包实验，两次跑的结果
没法比较。所以把弱网**搬进用户态**——在客户端与服务端之间架一个
帧级代理，按**确定性随机模型**（xorshift64*，同一种子同一序列）
注入丢包/延迟/乱序。Java 对照：`java.util.Random` 是 LCG 变体，
xorshift64* 更便宜（一次移位三连 + 乘法，约 3ns 无分配）且统计
质量对帧级注入绰绰有余——**比统计质量更重要的是可重现**：
`--seed` 相同的两次实验，丢包序列逐帧一致。

### 2.3 对账纪律：计数对不上，压测作废

「带对账的压测才可信」（阶段 7 定下的纪律）在本章三个场景全部
兑现：conn-storm 的守恒校验（路由表在线数 == 保活袋大小，拆除后
路由表必须清零）两次抓到真实问题（§4.3 的墙 2 与墙 3 的诊断过程）；
weak-link 的发送侧收口（acked + failed == sent）与接收侧独立计数
（去重后的 received）。**对账不是仪式，是压测数据的质检员。**

## 三、代码走读：LatencyHist 分位数草图

```text
桶 0            : [0, 256)      步长 1     —— 小延迟精确到纳秒
桶 1            : [256, 512)    步长 1
桶 2            : [512, 1024)   步长 2
桶 b (b ≥ 1)    : [256·2^(b-1), 256·2^b)  步长 2^(b-1)
...
桶 56           : 覆盖到 u64 顶端
```

三个设计决策值得咀嚼：

- **每桶固定 256 槽**（`SIGNIFICANT_BITS = 8`）：任何值的记录误差
  相对值 ≤ 2⁻⁸ ≈ 0.39%——「有效位」参数就是 HdrHistogram 的
  significant value bits。**用相对误差而不是绝对误差**做预算，
  才能用一套参数同时覆盖 µs 级与 s 级延迟；
- **查询返回槽的下界**（保守口径：真实分位数 ≥ 报告值）——压测
  数字宁可报低不可报高，这是测量工具的职业道德；
- **min/max 精确记录、不经过桶**：两端极值对抖动分析的价值远高于
  0.39% 的精度，且各只占一个 u64。

记录口径全程整数纳秒（u64 足装 584 年）——**测量代码不掺浮点**
（避免浮点误差污染对账与格式化，项目 cast 纪律见 docs/20 §7.2）。

单测守四件事：槽计数之和 == 总数（守恒）、分位数单调、精度界
（`locate`/`bucket_value` 往返一致）、与排序数组的基准真值在一步
之内吻合（`matches_sorted_ground_truth_within_one_step`——新旧两代
分位数工具互为对方的基准）。

## 四、conn-storm：M1 十万连接

### 4.1 场景设计

与 group-fanout（测扇出**热路径**）分工：conn-storm 测**规模**——
真实 TCP 三次握手 + 真实握手帧走完整服务端路径（网关 task + 会话
task + 路由注册），四个测量点：

1. 建连速率（风暴口径：多快接入 N 条连接）；
2. **每连接内存成本**（三级里程碑的核心账本——纵向天花板由
   `内存/连接` 决定）；
3. 稳态保持（hold 阶段连接不掉、内存不涨）；
4. 拆除（drop 全部连接后路由表清零——回收不泄漏的证明）。

诚实口径：

- 客户端与服务端**同进程**（回环 TCP），每连接成本 = 客户端半连接 +
  服务端全套（网关 task + 会话 task + 双向通道），报告按「每连接
  总成本」陈述——比单侧口径保守，不美化；
- 服务端有 60s 读空闲断连纪律：压测连接由 **20s 一次的 Ping 扫掠**
  保活（心跳不参与 seq 去重，seq 0 即可；10 万目标的建连相本身就
  超过 60s，「客户端不发心跳」的旧假设只在 1 万规模成立）；
- 内存采样用 Windows 工作集（`memstats.rs`），基线 → 稳态差值 /
  连接数 = 每连接成本（整数 KiB 口径）。

### 4.2 用法

```powershell
cargo run -p im-bench --release -- conn-storm                        # 1 万基线
cargo run -p im-bench --release -- conn-storm --connections 100000 --source-ips 7   # M1
# 完整参数：--wave 250 --hold-secs 5 --handshake-timeout-ms 5000
```

### 4.3 达成之前的四堵墙（真实优化过程）

M1 不是一次跑成的。四次实测、三个环境边界、两次判别实验——
**每一个瓶颈都是压测守恒校验或数据形状逼出来的**，全过程记录如下
（这正是 roadmap 承诺的「真实的优化过程比口号有价值」）。

**墙 0（1 万基线，先证明工具是对的）**

```text
建立: 10,000 连接 · 每连接 31.21 KiB（双端）· 握手 37,236 连接/秒 · 建连 477 连接/秒
```

**墙 1：动态端口池只有 13,977 个（os error 10055）**

10 万第一跑到 **13,919** 连接处 86,081 次 `connect: ... (os error 10055)`
（WSAENOBUFS）。端口侦查：本机的 TCP 动态端口范围被配置为
**1024 起、共 13,977 个**（`netsh int ipv4 show dynamicport tcp`；
默认应为 49152~65535 共 16,384）——13,977 − 58 已占用 = 13,919，
分毫不差。**是客户端临时端口耗尽，不是服务端能力**（握手相
33,425/秒健康）。处理：调宽至 10000~65535（55,536 个，需要
管理员权限；**压完已还原原配置**——netsh 改的是系统全局状态，
用完不还就是给机器留坑）。

**墙 2：60s 读空闲纪律回收了早期连接（守恒校验抓到）**

第二跑建满 **55,497** 连接，但守恒校验炸了：路由表 21,247 vs
保活连接 55,497——三万多连接 TCP 建立了、握手没完成。根因：
「客户端不发心跳」的假设被规模推翻——10 万目标的风暴建连相
≈125s > 服务端 60s 读空闲纪律，早期波次的连接在风暴结束前就被
空闲回收了。修复：**20s 一次的 Ping 保活扫掠**（建连相与 hold
阶段都扫掠；`--hold-secs` 上限仍 45s——扫掠不豁免拆除验证）。

**墙 3：三次撞同一堵 55.5k 的墙——Windows 的动态端口池是全局共享的**

第三跑（7 源 IP）依然停在 **55,487**。判别实验两连：

1. 3000 连接 + 3 源 IP，`Get-NetTCPConnection` 实证轮换**生效**
   （127.0.0.1/2/3 各 1000 条）——排除「轮换没绑上」；
2. 60000 目标 + 2 源 IP → 停在 **55,490**。

三跑数字 55,497 / 55,487 / 55,490 全部 ≈ 55,536（调宽后的池容量）。
唯一自洽的结论：**Windows 的动态端口池是全局共享的，不按源地址
分区**（与 Linux 相反）——源 IP 轮换在 Linux 上能成倍扩容，在
Windows 上换不来一个新端口。这是 10055 的第二张面孔：同一错误码，
第一跑是「单 IP 端口耗尽」，第三跑是「全局池耗尽」。

**解法：显式 bind 源端口**

动态端口池只约束**自动分配**；显式 `bind(源地址, 源端口)` 不受它
约束。`source_addr` 给每条连接分配「源 IP 轮换 + 显式源端口」：
每个源 IP 独享 20000..=65535 共 45,536 个端口，7 源 IP 容量
31.8 万。这是压测工程的常规手段（Linux 上不需要，因为自动分配
按地址分区——一次压测顺带搞清了两个平台的内核差异）。

### 4.4 第四跑原始数据（2026-09-25，M1 达成）

```text
目标            : 100000 连接（波 250，源 IP 7，逻辑核 16）
建立            : 99,969 连接，风暴墙钟 377.55s
建连相          : 351.43s（284 连接/秒）
握手相          : 2.12s（47,117 连接/秒）
失败            : 31 次（按原因分类）：
  [  28] connect: 以一种访问权限不允许的方式做了一个访问套接字的尝试。(os error 10013)
  [   3] connect: 通常每个套接字地址(协议/网络地址/端口)只允许使用一次。(os error 10048)
内存账本        : 基线 5.81 MiB → 稳态 5s 2894.81 MiB（Δ 2889.00 MiB）
每连接成本      : 29.59 KiB（含客户端半连接 + 服务端全套）
拆除            : 99,969 连接，6.02s，路由表清零: true
口径说明        : 同进程回环（每连接含双端成本）；数据归档 docs/16
```

（99,969 + 31 = 100,000 守恒；28 次 10013 是 Windows 的保留端口段
——`netsh int ipv4 show excludedportrange` 可查，避开头像段是后续
工程化项；3 次 10048 是显式端口与在用端口偶发相撞，失败如实计入
报告而非重试掩盖。）

### 4.5 结论

- **M1 达成**：99,969 / 100,000（99.97%），四堵墙全是**环境边界**
  而非架构边界——服务端全套（网关 task + 会话 task + 路由表行 +
  双向通道）在 10 万在位时握手相仍有 47,117/秒；
- **每连接 29.59 KiB（双端口径）**：外推 100 万连接 ≈ 29 GiB 工作集
  ——单机放得下内存，但 M2 需要把每连接压到 KB 级（缓冲池化、
  task 合并、io_uring）才能企及 C10M 的内存预算；
- **拆除 6.02s 全部清零**：10 万连接的回收不泄漏——drop 的所有权
  链条（连接 → 网关 task 退出 → 会话 task 退出 → 路由表反注册）
  在规模下依然成立，这是 Rust「以所有权管理生命周期」在 10 万
  数量级上的验证；
- **建连相变慢（477 → 284 连接/秒）**：10 万在位连接后每次 connect
  的内核路径变慢（全局连接表查找、非分页池碎片）——瓶颈在内核
  不在用户态，M2 的 io_uring 正是冲这层去的。

## 五、weak-link：弱网可靠性实测

### 5.1 场景设计

在客户端与服务端之间架一个**帧级**弱网代理：

- **丢包**（`--loss-permille`）：整帧丢弃（字节级丢包会把流内字节
  撕开，后续所有帧校验失败——那测的是「协议如何死于字节损坏」，
  不是「应用如何在帧丢失下自愈」；IM 的可靠性语义全部以帧为单位，
  注入也以帧为单位）；
- **延迟**（`--rtt-ms`）：单向注入 RTT/2；
- **乱序**（`--jitter-ms`）：0..jitter 均匀抖动叠加在延迟上，到达
  时刻交错自然产生乱序——调度侧用**小顶堆**按时出队（roadmap §4.5
  的落点），抖动为零时入队序做平局裁决严格保序。

被测路径是真实的：两个完整的 `im_client::run_client`（连接状态机、
重发表、指数退避、本地库、接收去重全套）穿过弱网代理连到真正的
`im_server`。压测工具只做三件事：发消息、数事件、对账。

### 5.2 用法

```powershell
cargo run -p im-bench --release -- weak-link          # 默认：200 条 · 双向 10% 丢包 · 100ms RTT
# 完整参数：--loss-permille 100 --rtt-ms 100 --jitter-ms 0 --seed 20260925
#           --retry-timeout-ms 300 --retry-max-attempts 8 --deadline-secs 120
```

### 5.3 一个不该被接受的数字：29.5%

默认场景第一跑（修复前）：

```text
发送 200 · 服务端确认 58 · 放弃 140 · 端到端到达率 29.5% · 平均尝试 5.90 次 · P50 124.78ms
```

这个数字**不该被直接采信**。数量级疑点：双向 10% 丢包下一次尝试
失败（上行丢失或 Ack 下行丢失）的概率 = 1 − 0.9×0.9 = 0.19，8 次
尝试全失败的概率 ≈ 0.19⁸ ≈ 2×10⁻⁶——200 条消息期望放弃数 ≈ 0.0004，
实测 140，**差 5 个数量级**。要么丢包模型坏了，要么系统里有一个
与「随机丢包」完全不同的系统性故障。

两个判别实验隔离变量：

1. `--loss-permille 0`（零丢包）：200/200 全达、0 重连、P50 ≈ RTT
   ——排除「心跳/重连机制自爆」；
2. `--rtt-ms 0 --loss-permille 100`（零延迟 + 10% 丢包）：到达率
   **仍是 29%**（ack 58、放弃 142、0 重连）——不是延迟、不是重连，
   是**系统性分区**。

数据内部自洽，形状指向病灶：142×8（重试全灭）+ 58（首试即过）= 1,194 =
   实际上行帧数——**二值分裂**，没有「试 3 次成功」的中间态；
   58 ≈ 64（去重窗口尺寸）× 90%（下行存活率）——窗口被楔死前恰好
   收下的条数。两个数字都指向同一片代码。

### 5.4 根因：接收窗静默楔死

完整因果链（每一步都有代码与数据背书）：

1. 帧级丢包在服务端 `DedupWindow`（位图窗口，尺寸 64）**前方留下
   一个洞**；
2. 洞**永不回填**：客户端应用层重传用的是**新 seq**（旧 seq 没人
   重发——seq 的语义是「帧序号」不是「消息 ID」，`client_msg_id`
   才是重传的核销键）；
3. 洞后第 64 帧起全部 `Verdict::TooFar`（超窗）；
4. 原实现对超窗的处理是**静默丢弃**（`continue`）——窗口永久楔死
   在洞口；
5. 最阴险的一步：**心跳 Ping/Pong 不参与 seq 去重**（设计如此——
   心跳无 seq 语义负担），于是连接表面健康、PING-PONG 正常，
   **上行业务帧全军覆没而无人报警**——静默失败。

`MsgAck` 的语义掩盖了问题的一半：Ack 表示「服务端已接收」与投递
成败解耦；而被楔死的连接连 Ack 都回不出来（上行 Msg 到不了
`handle_msg`），客户端 8 次重传耗尽后放弃——这就是 142 条放弃的
由来。

### 5.5 修复：TooFar → 重同步

`DedupWindow::resync(seq)`（`im-transport/src/dedup.rs`）：以到达
帧 seq 为新基准重建窗口（`rcv_nxt = seq+1`，位图清零）。`TooFar`
的文档本来就这么建议（「调用方应考虑重同步」）——三个接入点兑现：

- TCP 网关（`session.rs` 的 `serve_connection`）：`TooFar { .. } =>
  state.resync(frame.seq)`（完整论证在代码注释里）；
- WS 网关（`web/ws.rs`）：同款修改（两条接入路径同病同治）；
- 被跳过区间里的重复投递由**业务层按 `client_msg_id` 去重**兜底
  ——消息级去重与帧级去重是两层不同的保护，重同步交出帧级保护
  的窗口、保留消息级的幂等，「至少一次」语义天然兼容。

回归测试三层：dedup 单测（重锚后按序继续、旧帧判重复、u64::MAX
回绕安全）、会话级（seq 跳 80 → 81 超窗 → 重同步 → 82 按序收下 →
旧 seq 4 静默）、场景级（80 条 > 窗口 64 的消息在双向 10% 丢包下
failed == 0——修复前这个测试必挂）。

### 5.6 修复后数据与「90% 边界」的解读

```text
发送 200 · 服务端确认 200/200 · 放弃 0 · 平均尝试 1.23 次 · 上行帧 247
端到端延迟：min 118.83ms · P50 120.32ms · P90 120.58ms · P99 1.03s · max 1.03s · mean 156.48ms
端到端到达率：90.0%（180/200）
```

- **上行已经 100%**：200/200 确认、0 放弃——重传闭环打穿了
  10% 双向丢包（平均 1.23 次尝试 ≈ 1/0.9 的理论值）；
- **P99 1.03s 是重传的延迟签名**：300ms RTO + 600ms 退避 + RTT
  ——首试即过的 90% 落在 P50 ≈ RTT，重传一次的 9% 落在 P99；
- **端到端 90.0% = 200 × 下行单次存活 0.9**——残余 10% 是**下行
  单次投递边界**，不是缺陷：服务端的 `deliver` 是 fire-and-forget
  （写进出站通道成功即视为送达），下行投递帧丢失后无人重传。
  「可靠」的完整语义需要**下行投递的 ACK 闭环 + 离线补投**——
  记为明确欠账（阶段 12+ 候选项），不冒充 99.999%。

### 5.7 方法论小结（可复用的排查路径）

```text
数量级疑点（理论 2×10⁻⁶ vs 实测 140——差 5 个数量级，拒绝采信"边界"）
  → 判别实验 1（零丢包全绿：排除机制自爆）
  → 判别实验 2（零延迟仍 29%：隔离出"系统性分区"）
  → 数据形状（二值分裂 142×8+58=1194；58≈64×0.9 精确吻合窗口尺寸）
  → 读码定位（TooFar 静默丢弃 + 洞不回填 + 心跳掩盖）
  → 修复 + 三层回归 + 复测（数字精确自洽：90.0% = 200×0.9）
```

压测的价值不在报告里的数字，而在**数字与理论对不上的那一刻**。

## 六、算法/数据结构/设计模式落点（对照 roadmap §4.5）

| 落点 | 形态 | 位置 |
|------|------|------|
| 基数估计与分位数（HdrHistogram 思想） | 对数分桶 + 桶内 256 槽，相对误差 ≤ 0.39%，固定 114KB | `histogram.rs` |
| 小顶堆按时出队 | 弱网调度侧：`(到达时刻, 入队序, 帧)`，入队序做平局裁决保序 | `weaklink.rs` |
| 概率丢包模型（确定性随机） | xorshift64*：移位三连 + 乘法混合，同种子同序列 | `weaklink.rs` |
| 策略（Strategy） | 弱网损伤注入参数化（丢包/延迟/乱序三个独立维度自由组合） | `weaklink.rs` |
| 位图滑动窗口的自愈 | `resync` 重锚：窗口语义不变，超窗从"丢弃"升级为"重同步" | `dedup.rs` |

## 七、已知取舍（诚实的账单）

- **下行投递不重传**（端到端 90% 边界）：上行有 ACK + 重传闭环，
  下行投递是 fire-and-forget。99.999% 需要「投递 ACK + 离线补投」
  双件套——语义上等价于把离线队列从「离线才存」扩成「未确认即存」，
  是一个不小的工程，记为阶段 12+ 的候选欠账；
- **重同步交出被跳过区间的帧级去重**：业务层 `client_msg_id` 去重
  兜底。窗口语义（按序、乱序缓存、重复检测）对正常区间不变——
  只在「窗口已经楔死」的病态下才触发重锚，取舍面积极小；
- **conn-storm 的保活是扫掠不是心跳**：20s 一次批量 Ping 是「心跳
  的形状」而非真实客户端的独立心跳定时器——省 10 万个定时器，
  代价是建连相的写放大（可忽略：每扫掠 10 万帧 × 16 字节）；
- **M2/M3 未开工**：io_uring 与 SO_REUSEPORT 多进程都是 Linux 平台
  的工作，Windows 上的里程碑记录到 M1 为止（10013 保留端口段、
  全局动态端口池两堵墙也已记录）——**在哪个平台就诚实说哪个
  平台的数字**；
- **每连接 29.59 KiB 离 KB 级目标尚远**：含双端（单侧 ≈15 KiB），
  优化方向是缓冲池化与 task 合并，属 M2 课题。

## 九、开发中踩过的坑

- **Windows 动态端口池全局共享**：源 IP 轮换换不来新端口（Linux
  相反）——三跑撞同一堵 55.5k 的墙才逼出这个平台差异，判别实验
  与解法见 §4.3。**两个平台内核行为不同的假设，只能用实验分辨，
  不能靠文档记忆**；
- **netsh 改的是系统全局状态**：压测调宽动态端口范围后**必须还原**
  （本机原配置 1024/13977），否则就是给机器留坑；同理 UAC 提权
  操作要记录在案；
- **10055 的两张面孔**：同一个错误码，第一跑是「单 IP 端口耗尽」，
  第三跑是「全局池耗尽」——错误码只告诉你「哪类资源不够」，
  不告诉你「哪个资源不够」；
- **「客户端不发心跳」的假设随规模失效**：1 万规模 45s 内建完，
  60s 空闲纪律不构成威胁；10 万规模建连相 125s，早期连接全被
  回收——**压测工具的每个假设都要在目标规模下重审**；
- **接收窗楔死**（本章主角，完整因果链见 §5.4）：静默失败的教科书
  案例——心跳不参与 seq 去重是合理的省事设计，但它同时掩盖了
  上行全死的病态。完整条目收录于 docs/20。

## 十一、面试题与标准回答

**Q1：为什么压测要用分位数草图（HdrHistogram）而不是把样本存下来排序？**

答：三个理由。资源：百万样本的排序数组是几十 MB 的堆分配与
O(n log n) 的查询，压测工具自己变成了被测系统的竞争者（观察者
效应）；草图是固定 114KB、O(1) 记录。语义：延迟分布要的是分位数
不是逐样本，对数分桶 + 桶内线性细分能把**相对误差**控制在 0.39%
——用相对误差预算才能一套参数同时覆盖 µs 级与 s 级。纪律：查询
返回槽下界（保守口径），压测数字宁可报低不报高。Java 对照就是
JMH 生态的 HdrHistogram（Gil Tene），本项目从零实现了它的骨架。

**Q2：10 万连接的「每连接内存成本」怎么测才可信？**

答：四个纪律。口径先说清：客户端与服务端同进程回环，所以数字是
「双端合计」——比单侧口径保守，报告里必须写明（不美化）；基线
差值法：先采空闲基线，稳态期再采样，差值除以连接数——绝对值没有
意义，增量才有意义；平台原语：Windows 用工作集（ProcessMemoryInfo），
不做跨平台假设；守恒对账：连接数、路由表行数、拆除后清零三者必须
闭环——对不上的压测数据直接作废。本项目实测 29.59 KiB/连接
（双端），外推百万连接 ≈29 GiB，据此判断 M2 的优化方向在缓冲
池化与 task 合并。

**Q3：弱网模拟为什么要做在用户态、帧级，而不是用 tc netem 或拔网线？**

答：可重现性与语义正确性。可重现：xorshift64* 确定性随机，
同一种子逐帧复现同一丢包序列——公网/netem 的两次实验不可比较，
用户态代理的两次实验可以精确 diff。语义：IM 的可靠性机制（seq
去重、client_msg_id 核销、指数退避）全部以**帧**为单位，字节级
注入会把流内字节撕开、后续帧全部校验失败，测的是「协议怎么死于
字节损坏」而不是「应用如何在帧丢失下自愈」。控制变量：丢包/
延迟/乱序三个维度独立可调——正是靠「零丢包」「零延迟」两个判别
实验，才把 29.5% 的异常到达率隔离成「系统性分区」并最终定位到
接收窗楔死（§5）。tc netem 是真网测试的好工具，但**排障需要的是
可操控的变量，不是真实感**。

**Q4：讲一个你压测发现的真实缺陷。**

答：双向 10% 丢包下端到端到达率 29.5%，而理论放弃率是 2×10⁻⁶
——差 5 个数量级，这个数字不能采信。判别实验排除机制自爆（零
丢包全绿）与延迟/重连（零延迟仍 29%）；数据形状是二值分裂
（142×8+58=1194 帧，无中间态；58≈64×0.9 与窗口尺寸精确吻合）；
读码定位：帧级丢包在 DedupWindow 前方留下**永不回填的洞**（应用层
重传用新 seq），洞后第 64 帧起全部超窗，原实现静默丢弃——窗口
永久楔死；而心跳不参与 seq 去重，连接表面健康、上行全死，**静默
失败**。修复是超窗从「丢弃」升级为「重同步」（dedup 文档本来就
这么建议），三层回归测试 + 复测：200/200 确认、0 放弃、到达率
90.0% = 200×下行单次 0.9，残余是「下行不重传」的已知边界而非
缺陷。这个案例的方法论：**压测的价值不在数字，在数字与理论对不
上的那一刻**。

**Q5：Windows 和 Linux 的高并发压测有什么实际差异？**

答：踩过的三个。临时端口池：Linux 按源地址分区（bind 不同源 IP
就能成倍扩容）；Windows **全局共享**——源 IP 轮换换不来一个新
端口，10 万连接必须显式 bind 源端口（三跑撞同一堵 55.5k 的墙 +
两个判别实验才确认，两个平台的内核差异只能实验分辨不能靠记忆）。
端口范围配置：Windows 是 `netsh int ipv4 set dynamicport`（本机被
配置成 1024/13977 而非默认 49152-65535，第一跑 13,919 处 10055
就是这个），改完必须还原——系统全局状态用完不还就是留坑。再往
上是平台选型：M2 的 io_uring、SO_REUSEPORT 多进程都是 Linux 的
能力面，Windows 的记录到 M1 为止——**在哪个平台就诚实说哪个平台
的数字**，这比「我们支持百万连接」的口号值钱。
