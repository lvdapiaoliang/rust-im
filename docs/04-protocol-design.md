# 04 - im-protocol 协议层设计（阶段 1）

> 对应代码：`crates/im-protocol/` ｜ 前置阅读：`docs/00-roadmap.md` 4.5 节算法图谱
> 学习配套：`learning-rust-from-scratch/04-algorithms/`（数据结构）、`05-patterns/`（设计模式）

## 一、这一层解决什么问题

IM 的最小可靠单元是**帧（frame）**：一条心跳、一条消息、一次 ACK 都是帧。
但 TCP 给我们的只是无结构的字节流——"粘包/半包"是常态：

```text
发送方写了两次:  [帧A] [帧B]
接收方可能读到:  [帧A的一半] | [帧A剩下一半+帧B] | [帧B的一半]
```

协议层的职责：**字节流 ↔ 帧** 的双向转换，并在这个过程中做到
尽早发现错流（magic/版本）、拒绝恶意输入（长度上限）、校验完整性（CRC）。
它是**纯逻辑 crate**——不碰 IO，因此测试不需要网络，
未来从 TCP 换 QUIC 时这一层原封不动。

## 二、线上帧格式

```text
┌────────┬────────┬──────┬───────┬────────┬────────┬────────┬─────────┬───────┐
│ magic  │version │ cmd  │ flags │  seq   │  ack   │  len   │ payload │ crc32 │
│ 2 byte│ 1 byte │1 byte│1 byte │ varint │ varint │ varint │ len byte│4 byte│
└────────┴────────┴──────┴───────┴────────┴────────┴────────┴─────────┴───────┘
 大端      1       枚举    位标志                                覆盖前面所有字节
"IM"=0x494D
```

每个设计决定的理由：

| 决定 | 为什么 |
|---|---|
| magic 2 字节 | 错连到 HTTP/Redis 端口时**第一个字节就能发现**，不用等解析失败 |
| version 1 字节 | 协议演进的协商基础；不兼容变更递增版本而不是猜 |
| cmd 用 enum | 未知命令在解码边界报错（`TryFrom<u8>`），不污染业务层 |
| seq/ack/len 用 varint | 心跳帧从 29 字节缩到 **12 字节**（-58%）；带宽与内存双省 |
| CRC-32 覆盖除自身外全部 | 单一字段校验整帧完整性；检错语义覆盖链路突发误码 |
| 无 payload 时帧仅 12 字节 | 心跳是 IM 最高频帧——它越小，百万连接下的常态开销越低 |

**seq/ack 语义**（与 TCP 同族，阶段 3 实现滑动窗口时展开）：
发送方每帧 `seq` 单调 +1；接收方回 `ack = 已连续收到的最大 seq + 1`，
即"ack 之前的我全收到了"。去重窗口、补发、离线同步全部建立在这对字段上。

| 模块 | 算法图谱 | 设计模式图谱 |

### 3.1 varint：小数字的空间经济学

u64 定长 8 字节，但 IM 里 99% 的 seq < 16M（varint ≤ 4 字节）。
varint 每字节存 7 位、最高位作"还有后续"标志。
zigzag 让有符号数（未来的时间差字段）避免 `-1` 编码成 10 字节的坑。

### 3.2 CRC32：为什么不是哈希/校验和

- 求和校验和发现不了**字节重排**；CRC 能检出所有 ≤32 位突发错误；
- MD5/SHA 防**篡改**（那是阶段 7 E2EE 的事），防**误码**用 CRC 快一个数量级；
- 与 zlib/PNG 同参数：`crc32("123456789") == 0xCBF43926`，可直接对拍。

### 3.3 解码状态机：增量消费的艺术

`FrameDecoder` 的核心是 `Stage` 枚举——**解析进度被编码进类型**：

```text
Header(5B 校验) → Seq → Ack → Len(此处检查上限!) → Payload → Crc → 出帧
                   └──────── 任意阶段字节不够就暂停，保留进度等下一次喂入 ────────┘
```

两个关键防护：
1. **长度上限在分配内存之前检查**——恶意 `len` 字段骗不走 1 GiB 分配；
2. **CRC 增量累积**——每消费一段字节就喂给 `Crc32`，帧尾到达即得结果，不回头重扫。

开发中实际踩过的坑（值得记住）：`feed_varint` 最初一次只吐一个字节，
把「varint 未结束」误当成「缓冲区耗尽」提前返回——单字节 varint 的单元测试
全部通过，**多字节 varint 的 proptest 才暴露它**。性质测试的价值现场。

## 四、测试策略

| 层次 | 手段 | 覆盖 |
|---|---|---|
| 已知向量 | 教科书用例（varint 300→`[0xAC,0x02]`、CRC `"123456789"`） | 算法正确性 |
| 逐字节喂入 | 一帧拆到一字节一次 | 半包最坏情况 |
| 任意切分 | proptest：任意 seq/ack/payload × 任意 split 点 | **解码与切分点无关**（数学性质） |
| 两帧三段 | 粘包 + 混合切分 | 多帧缓冲区管理 |
| 攻击路径 | 假 magic / 坏版本 / 未知 cmd / 超长 len / 翻转 payload / 翻转 CRC | 全部错误分支 |

proptest 失败会自动写入 `proptest-regressions/`，变成永久回归用例。

## 五、性能注记（阶段 1 不做基准，先记下预期）

- 编码：零分配路径（`encode_into` 到复用的 `BytesMut`），varint/CRC 全在栈上；
- 解码：每字节常数时间处理，`Bytes::freeze()` 出帧后克隆零拷贝；
- 预期单帧编解码 < 200ns（阶段 9 用 criterion 验证，超了再优化）。

## 六、下一步（阶段 2 预告）

协议层已就绪，但它还不认识 TCP。阶段 2（`im-transport`）将把
`FrameDecoder` 接进 tokio 的 `TcpStream` 读循环，加上
超时/心跳调度、优雅关闭——echo 服务器将进化成第一个"会说话"的 IM 网关。
