# 15 · 群会议与屏幕共享（阶段 9）

> 阅读前置：docs/14 §二（P2P 拓扑的天花板——正是本章换拓扑的动因）、
> docs/12 §三（REST 端点表）。
> 本章代码入口：`crates/im-server/src/web/meeting.rs`（JWT 手签）、
> `web/src/stores/meeting.ts`（SFU 连接编排）、`deploy/`（LiveKit 部署）。

## 一、本章目标

阶段 8 交付了 1对1 的 P2P 实时媒体。本章把它扩展到「一对多」：

- 群会议：任意成员随时进入，音视频 + 屏幕共享，走 LiveKit SFU；
- 服务端只加**一个端点 + 一个纯计算模块**（约 150 行，无新表、无新信封）：
  `POST /api/groups/{id}/meeting/token` → 签发入会 JWT；
- 屏幕共享从阶段 8 的「通话特殊形态」回归为「会议的一个普通 track」。

## 二、概念：P2P、MCU、SFU——三拓扑的成本账

N 人互看，媒体怎么走？三条路线（Java 工程师对照：这就是消息队列里
点对点 / broker 汇聚 / Kafka 分区的取舍问题——**拓扑决定成本曲
线**）：

| 拓扑 | 每人上行 | 服务器带宽 | 服务器 CPU | 延迟 |
|---|---|---|---|---|
| **P2P 全连接**（mesh） | N-1 路 | 0 | 0 | 最优（一跳） |
| **MCU**（混流） | 1 路 | 下行 N 路（1 路合流） | 编解码合流，很贵 | 较差（合流耗时） |
| **SFU**（选择性转发） | 1 路 | 上行 N 路 × 下行 N 路 | 只转发不编码，便宜 | 接近 P2P（仍一跳转发） |

数值感受：8 人 1080p 会议，P2P 要每端上行 7×3Mbps = 21Mbps——家用
宽带直接出局；SFU 只要 3Mbps（进服务器），服务器总带宽
8×7×3 = 168Mbps（每路视频进一次出七次）——一台普通虚机扛几十路
会议。**MCU 是电话会议时代的遗产**（省客户端算力，服务器做混流），
如今客户端解码能力过剩，SFU 是事实标准；LiveKit、mediasoup、
Janus 都属此类。

我们的定位分工：**LiveKit 是「会转发视频的 im-bench」**——im-bench
量的是我们扇出 actor 的吞吐，LiveKit 量的是 SFU 转发的吞吐，两者
我们都不自己写媒体层。自建 im-server 里剩下的、也是必须自建的部分：
**准入裁决**（是不是群成员）与**凭据签发**（JWT）。

## 三、架构：领票制

```text
Vue 前端                im-server（axum）              LiveKit SFU
  │ POST /api/groups/{id}/meeting/token                  │
  │ ────────────────────────────────▶ is_member 点查     │
  │                                 （成员表=唯一真相源）  │
  │ ◀── { token, url, room } ───────  手签 JWT（HS256）   │
  │                                                      │
  │ room.connect(url, token) ──────────────────────────▶ │ 验签 + 验 grants
  │ ◀═════ WebRTC 媒体（每人上行一路，SFU 选择性转发）═════ │
```

三个设计决策：

- **认证与转发分权**：SFU 只验签（你拿的是不是用真 secret 签的票），
  不裁决资格；「谁能领票」在我们这（is_member 点查——与消息门槛、
  成员列表同一纪律第三次落地）。持有 LiveKit secret 就能替任何人
  签票，所以 secret 只活在服务端环境变量里；
- **一群一间常驻会议室**（room 名 = `im-meeting-{群 ID}`）：不建
  「会议」表、没有开始/结束状态机——谁先带票进去谁就「开始」了，
  最后一人离开后 LiveKit 自动回收房间。**把状态推给有天然生命周期的
  一方**（房间随人走空而亡），比在 DB 里维护会议状态机省一整个域；
- **配置不出服务端**：前端拿到的 `{token, url, room}` 三件套里没有
  API key/secret——凭据即权力，签好的票可以给（短时效、带房间与
  身份绑定），钥匙不能给。

## 四、代码走读

### 4.1 手签 JWT：为什么不用 jsonwebtoken（meeting.rs）

入会令牌是标准 JWT（HS256）：`base64url(header).base64url(claims).
base64url(HMAC-SHA256(前两段))`。依赖只差 HMAC 与 base64url——
前者 20 行（RFC 2104：`H(K⊕opad, H(K⊕ipad, msg))`，密钥超 64 字节
先哈希），后者 15 行（6 位一组的位打包）。**签名是安全边界**，
亲手写一遍才知道边界在哪——并且正确性不靠目测：HMAC 用 RFC 4231
官方测试向量验证（含「密钥超块大小」分支），base64url 用 RFC 4648
边界向量验证。这与阶段 0 手写帧编解码是同一理由：**造轮子的价值
在理解，不在替代**（生产里该用审计过的库——这句话同样写进了代码
注释）。

claims 里的 `video` 字段是 LiveKit 的授权载荷（grants）：`roomJoin` +
房间名 + `canPublish`/`canSubscribe` 双许可；`sub` 填用户 ID（串化——
与全项目「雪花 ID 在 JSON 里一律字符串」的约定一致）、`name` 填昵称
（会议界面显示名）。TTL 2 小时：比登录令牌 7 天短得多——会议令牌
的暴露半径是「一间房、一场会」，过期就废，不需要撤销机制。

### 4.2 端点：一个处理器的三步（api.rs::meeting_token）

`is_member` 点查 → `room_name` 派生 → `sign_meeting_token` 组装。
没有事务、没有队列、没有写路径——一个纯函数式的「售票窗口」。
对照阶段 7 `add_group_member`（写路径要打脏扇出快照），读路径的
简单是干净挣来的。

### 4.3 前端：轨道编排（meeting.ts）

livekit-client 的 `Room` 接管了阶段 8 我们手写的全部协商——offer/
answer/ICE/重连/订阅信令都不用碰了（**它们没消失，只是进了库**——
这与阶段 8 用浏览器原生 WebRTC 而不自写 SRTP 是同一分层）。
我们要做的只剩编排：

- 领票失败（非成员 403）与连接失败（无 LiveKit 服务）统一进
  `error` 展示——两条失败路径在 UI 上只有一个「连不上」出口；
- 远端轨道按成员合流成 `MediaStream`（`<video>` 元素音视频通吃），
  事件回调是唯一写入点：TrackSubscribed 合入、Unsubscribed 摘除、
  ParticipantDisconnected 整卡删除——**单一写入者的纪律**，与
  chat store 的 ingestIncoming 同款；
- 屏幕共享 = `setScreenShareEnabled(true)`，多发布一条 track 而
  已——SFU 时代它不是特殊形态，是普通轨道。

`Room` 对象同样不进 Vue 的 ref（命令式对象与深度代理不合——
阶段 8 的 `RTCPeerConnection` 同一条纪律，第三次出现）。

### 4.4 部署：deploy/ 的最小 LiveKit

`docker compose -f deploy/docker-compose.yml up -d` 一条命令起
SFU：信令 7880、RTC over TCP 7881、UDP 媒体端口段 50000-50100。
compose 里的 `devkey: secret` 与后端默认值互为镜像——**零配置跑通
本机演示**，生产换 `IM_LIVEKIT_*` 三个环境变量（代码不动）。

TURN 服务器在这里消失了：SFU 架构下媒体本来就进服务器，不存在
「打洞失败」这回事——**换拓扑顺手消灭一整类问题**（对照 docs/14
§八记录的「无 TURN」欠账，那份账单在会议场景下自动结清）。

## 五、设计模式实战（对照 roadmap 4.5）

| 模式 | 在本阶段的形态 |
|---|---|
| **门面（Facade）** | `POST /meeting/token` 把「查资格 + 派房间 + 签票」三个动作收敛成一个售票窗口；前端不认识 LiveKit 的鉴权协议，只认识三件套 |
| **委托（ outsourcing 的架构形态）** | 媒体转发外包给 LiveKit、准入裁决自留——把「必须自建的部分」（认证）与「可以采购的部分」（转发）划清，是本阶段最重要的架构决策 |
| **状态推给有天然生命周期的一方** | 会议无状态机：房间生死跟人走，DB 零新增表。对照：群消息的已读状态就该在 DB（生命周期跟会话走）——状态的归属跟着生命周期走，不是跟着功能走 |
| **单一写入者** | meeting store 的 remotes 只由事件回调写入（与 chat.ingestIncoming 同款）；JWT 只由 sign_meeting_token 一处产生 |

## 六、测试策略

| 层 | 用例 | 要点 |
|---|---|---|
| 纯函数单测 | HMAC-SHA256 对 RFC 4231 三个向量（含超块密钥分支） | 签名正确性不靠目测 |
| 纯函数单测 | base64url 对 RFC 4648 边界向量（1/2/3 字节尾块） | 尾块字符数是手写编码最常见的坑 |
| 纯函数单测 | JWT 三段结构：标准头解回 claims 验 iss/sub/room/grants + 签名可复算 | 自签自验只证确定性 |
| REST 集成（真 PG） | 成员领票 200（三段 token + 群派生房间名）；非成员 403；拉人后新成员即有资格 | 资格跟着成员表走 |
| 前端 | `vue-tsc` + `vite build` | 类型即测试 |
| 实机联调 | 起 LiveKit → 两浏览器进会同屏 | **未做**（见 §七） |

## 七、已知取舍（诚实的账单）

- **本机无 Docker，LiveKit 未实机联调**：开发机没有 Docker 环境，
  `deploy/` 的 compose 文件与后端默认凭据按官方文档配置并写明了
  验证步骤，但「起服务 → 领票 → 连接 → 同屏」的端到端链路没有
  真实跑过。JWT 互认的验证缺口由 §六的单测部分覆盖（HS256 是
  确定性算法，向量对齐即签名正确）；livekit-client 侧的连接参数
  按 SDK 文档编写，留待有 Docker 的环境做一次手工冒烟——
  **写明没验证过什么，和验证过什么一样重要**；
- **无白板/录制/举手**：会议产品形态的完整性欠账（同 docs/13 §七
  的群管理欠账并列）；
- **屏幕共享的授权**：任何成员都能共享（grants 里 canPublish 对
  所有成员一致）。真实产品会做「同一时刻只有一路共享」的仲裁
  ——LiveKit 支持 room-level 事件，属产品策略不是协议缺口；
- **令牌无撤销**：2 小时内踢人无效（TTL 是唯一的撤销手段）。
  教学取舍：真实做法是 LiveKit Admin API 的 RemoveParticipant，
  需要服务端持有 API secret 调 SFU 的 HTTP 接口——多一个集成面，
  收益是即时踢人。

## 九、面试题与标准回答

**Q1：为什么群会议不自研 SFU？你们不是在学底层吗？**

答：分两层。**第一层，媒体转发不是教学目标**：SFU 的核心是
jitter buffer、带宽估计（GCC）、SIMULCAST 分层转发——每一项都是
独立的大课题，自研一个能用的 SFU 是一年级量的工程，且教学价值
与 IM 项目的主线（协议/会话/扇出）不重叠。**第二层，自研了该自研
的部分**：准入裁决（is_member）、JWT 签发（手写 HMAC + 官方向量
验证）、与既有群的映射关系（一群一房）——这些是业务语义，外包
不了。判断标准：**这个能力是业务的还是行业的**？会话路由是业务的
（自建），媒体转发是行业的（采购/开源）——正如没有公司自建数据
库来存业务数据。

**Q2：会议安全靠什么？前端能拿到 token 会不会被滥用？**

答：三道闸。第一道，领票要带登录令牌且过 is_member（服务端裁决，
前端伪造无效）；第二道，JWT 绑定身份与房间（`sub` + `video.room`），
拿到票的 A 不能冒充 B 进会（SFU 按 claims 里的身份记账），也进不了
别的房间；第三道，TTL 2 小时——失窃票据的暴露窗口有限，且没有
撤销状态可被攻击（无状态令牌的撤销靠短时效，这是 JWT 的经典权衡，
对照登录令牌「存 DB 可撤销」是另一种取舍——**可撤销性和无状态性
不可兼得**，按场景选）。至于 API secret：只在服务端环境变量里，
签好的票可以给，钥匙不能给。

**Q3：P2P 和 SFU 你们的系统里都用了，什么时候选哪个？**

答：按参与方数量与上行带宽能力选。1对1：P2P（媒体不过服务器，
延迟最低、服务器零成本），我们的信令只做转发；N 方：SFU（P2P 全
连接的上行随人数线性恶化，8 人就到家用宽带上限）。**混用是常态而
非妥协**——Zoom 的 1对1 通话走 P2P、多人走云，Discord 语音小房间
P2P 大房间 SFU，同一引擎按人数切换拓扑。我们的实现里两种形态共享
阶段 8 的全部认知（getUserMedia/track/协商语义），切换的只是
「轨道往哪送」——**在正确的抽象层（MediaStreamTrack）上，拓扑
是配置而不是重写**。
