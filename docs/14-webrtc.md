# 14 · WebRTC 音视频与远程桌面（阶段 8）

> 阅读前置：docs/12 §四（WS 信封与 event 通道）、docs/13（服务端转发的
> 上限——正是本章换拓扑的动因）。
> 本章代码入口：`crates/im-server/src/web/ws.rs`（signal 信令转发）、
> `web/src/stores/call.ts`（WebRTC 状态机）、`web/src/components/CallOverlay.vue`。

## 一、本章目标

文本链路（单聊/好友/群聊/富媒体）完成后，IM 的另一半形态是实时媒体。
本章交付：1对1 音视频通话 + 远程桌面共享（WebRTC P2P）——

- 服务端只加一种信封：`signal`（信令中转，约 50 行）；
- 前端加一个 store（WebRTC 会话状态机）+ 一个覆盖层组件；
- **媒体流一比特都不经过我们的服务器**。

## 二、概念：为什么消息走服务端、媒体走 P2P

回顾阶段 7 的压测数字：单 actor 扇出天花板约 94 万人次/秒——文本
消息（百字节级、人手速频率）绰绰有余。但视频通话是完全不同的量级：

| 维度 | 文本消息 | 视频通话 |
|---|---|---|
| 码率 | ~百字节/条，几条/秒 | 0.5~2.5 Mbps/路（VP8/H.264） |
| 延迟要求 | 秒级可接受 | >300ms 就"不像对话" |
| 可靠性要求 | 一条都不能丢（ack + 离线补投） | 丢帧不如延迟——实时性 > 完整性 |
| 拓扑 | 服务端扇出（可控制、可审计、可补投） | 端到端直连（省带宽、低延迟） |

结论是**双拓扑分工**：信令（谁想跟谁通话、SDP/ICE 协商）走我们的
WS 通道——它低频、小载荷、要求可靠；媒体（音视频帧）走 WebRTC P2P
直连——它高频、大流量、要求低延迟。服务器在一场通话里的全部工作
是转发几十条几 KB 的信令，然后袖手旁观。

Java 工程师对照：这是「控制面 / 数据面分离」在 IM 里的实例——
SIP（信令）/ RTP（媒体）的分工、K8s 的 apiserver/kubelet、
SDN 的 controller/forwarder，同一个架构思想。

### 2.1 WebRTC 三件套（速览）

WebRTC 建立一条 P2P 媒体管道需要三步协商，全部经我们的信令通道转发：

1. **SDP offer/answer**（想通话）：呼叫方 `createOffer()` 生成本端
   媒体描述（编解码器、分辨率），经信令发给对方；对方 `createAnswer()`
   应答。双方各自 `setLocalDescription` / `setRemoteDescription`；
2. **ICE 候选交换**（怎么连通）：每端枚举自己的网络地址（本机 IP、
   NAT 公网映射——后者需要 STUN 服务器打听），每发现一个候选就
   实时发给对端；双方握手成功后选出第一条能通的路径；
3. **DTLS/SRTP**（自动完成）：连通后浏览器自动做密钥协商与加密——
   WebRTC 的媒体流**强制加密**，这层我们一行代码都不用写。

我们的服务器在第 1、2 步里只做**不透明转发**（与消息 content 同一
语义）：`signal` 字段是任意 JSON，服务端不解释。信令演进（如将来加
屏幕共享的 track 元数据、群通话的 SFU 编号）零服务端改动。

## 三、协议：signal 信封（服务端全景）

```text
呼叫方                                 服务端（ws.rs::handle_signal）        被呼方
  │ {"type":"signal","seq":n,                                             │
  │  "payload":{"to":"<B>","signal":{"call":"offer","sdp":"…"}}            │
  │ ─────────────────────────────────────────▶ │ 好友门槛（is_friend）      │
  │                                            │ 取 from = 呼叫方（裁决）    │
  │                                            │ ── event{kind:"signal" ─▶ │ 来电 UI
  │                                            │    from, signal} 原样转发  │
  │                              对方离线/非好友 │                            │
  │ ◀── error{code:"peer_offline"|"not_friend"}│                            │
  │                                            │ ◀── answer / candidate ── │ 接听/协商
  │ ◀── event{kind:"signal",…} ────────────────│                            │
  │        （candidate 双向乱序到达，直到 P2P 建立）                          │
  │ ════════════ 媒体流直连（DTLS/SRTP，服务器不经手）═════════════════════▶ │
```

三个协议决策（与 docs/12 的既有语义对齐）：

- **信令不是消息**：不分配 `msg_id`、不 ack、不进离线队列。ICE 候选
  五秒后到达就过期了——离线补投一条过期的 offer 只会让重连后的对端
  困惑。**实时性是信令的唯一价值**，可靠性由用户重拨保障。这与好友
  事件（"真相在数据库，推送只负责快"）是同一哲学的另一个切面；
- **下行复用 `event` 信封**（`kind = "signal"` 判别）：零新下行类型，
  前端事件订阅表天然扩展。`from` 由服务端裁决（伪造无效）——被呼方
  知道"谁在呼我"必须可信，否则来电显示就是摆设；
- **门槛与消息一致**（仅好友间）：通话权限不比消息宽松。校验在
  服务端 `handle_signal`（客户端校验只是装饰——同一纪律第 N 次）。

错误码新增 `peer_offline`（对端离线，即时反馈给呼叫方）。

## 四、代码走读

### 4.1 服务端：50 行的中转器

`ws.rs::handle_signal` 全部逻辑：解析 `to`/`signal` → `is_friend`
门槛 → `push_event(to, {kind:"signal", from, signal})` → 未送达回
`peer_offline`。没有 DB 写、没有队列、没有状态——**一场通话在
服务端没有实体**，这是 P2P 架构的优雅之处：媒体管道建立后，就算
我们的服务器重启，通话也继续（信令通道断了只是不能再协商新的）。

### 4.2 前端：通话状态机（call.ts）

```text
idle ──startCall──▶ calling ──answer──▶ connecting ──P2P 建立──▶ connected
  ▲                  │  │                                              │
  │   reject/离线/非好友└──────────────┐                               │
  │                                    ↓                               │
  └───incoming──accept──┘          cleanup（挂断/被拒/连接断开/SDP 失败）◀┘
```

几个值得咀嚼的实现决策：

- **`RTCPeerConnection` 不进 Vue 的 ref**：它是命令式对象，Vue 的
  深度代理会干扰其内部状态（EventTarget + 内部 slot）。状态机里
  用普通局部变量持有，`MediaStream` 才进 ref（模板要挂到
  `<video>`）——**框架边界感**：不是所有东西都该响应式；
- **offer 先到、candidate 后到是常态**：被呼方的 `ontrack`/
  `addIceCandidate` 由浏览器内部缓冲乱序，但"接听"是用户动作——
  offer 到达时就 `setRemoteDescription` 存好，candidate 随到随加；
- **媒体形态由 offer 携带**（`media: 'audio-video' | 'screen'`）：
  接听方据此决定要不要开摄像头。远程桌面（`getDisplayMedia`）场景
  接听方只看不发——**同一根 P2P 管道，两种产品形态**，协议不区分；
- **ICE 只配 STUN 无 TURN**：打洞失败（对称型 NAT，约 10~15% 的
  企业网络）就失败。TURN 中继是带宽成本 + 运维成本，教学项目把
  "没有 TURN 时通话会怎么失败"留给读者亲手观察（见 §七练习）；
- **正忙拒新呼叫**：通话中收到第三个 offer，礼貌回 `reject` 且
  **不触碰当前通话的任何状态**——并发信令的隔离与阶段 7 慢消费者
  隔离是同构问题（一份状态，多个写入者，保正在服务的那个）。

### 4.3 UI：CallOverlay 三态 + 失败提示态

覆盖层挂在 App.vue（来电可能发生在任何路由）；媒体挂载用命令式
`srcObject`（`<video :src>` 绑不了 MediaStream，watch 桥接）。
挂断原因（对方已挂断/拒绝了通话/不在线）在通话收摊后以**纯提示态**
保留展示——挂断不给理由的通话 UI 等于让用户猜谜。

## 五、设计模式实战（对照 roadmap 4.5）

| 模式 | 在本阶段的形态 |
|---|---|
| **状态机（State）** | call store 的五态机（idle/calling/incoming/connecting/connected），与连接生命周期（阶段 2）、发送状态机（阶段 4 前端）同一手法第三次落地 |
| **策略隐于配置** | ICE 服务器列表：换 TURN 只改一个常量数组——拓扑策略与状态机解耦 |
| **不透明转发（ Interpreter 的反面）** | 服务端对 signal 零解释：协议演进成本全部隔离在前端（与消息 content 同源策略，一个项目里用两次证明它是模式而非巧合） |
| **命令式/声明式分层** | RTCPeerConnection（命令式）与 Vue 状态（声明式）的边界管理：媒体对象不响应式、流挂载用 watch 桥接 |

## 六、测试策略

| 层 | 用例 | 要点 |
|---|---|---|
| WS 集成（真 WS + 真 PG） | 信令主线：好友间 offer 转发，`from` 裁决、载荷原样、发送方无回执 | 信令 ≠ 消息的协议验证 |
| WS 集成 | 非好友 → `not_friend`，对端零动静 | 门槛 |
| WS 集成 | 对端离线 → `peer_offline`，且不进离线队列（`offline_count == 0`） | 不补投的语义验证 |
| 前端 | `vue-tsc` + `vite build` | 类型即测试 |
| 真机 | 两浏览器互拨（摄像头 + 屏幕共享） | 手工冒烟（WebRTC 的协商行为无法在单测里复刻） |

服务端信令是可测的（无浏览器依赖），**WebRTC 本体不可单测**——
它的正确性由浏览器保证，我们只测自己写的协商编排。这个边界划分
让测试矩阵不至于爆炸。

## 七、动手练习

1. **观察 ICE 协商**：两浏览器开 DevTools → `chrome://webrtc-internals`，
   发起通话，观察 candidate 成对出现、`selected candidate pair` 高亮——
   把每条候选与 call.ts 发出的信令按时间对齐；
2. **复现打洞失败**：给 ICE_SERVERS 传空数组（`[]`），同机两个浏览器
   还能通吗？（提示：host 候选不依赖 STUN）再断开 Wi-Fi 试试；
3. **给远程桌面加"远程控制"**（进阶）：在 DataChannel 上实现
   事件回传（鼠标/键盘），被控端 `dispatchEvent` 回放——注意这是
   极高的安全权限，真实产品（TeamViewer/向日葵）如何做授权确认？

## 八、已知取舍（诚实的账单）

- **无 TURN**：对称型 NAT 后的通话会失败。生产要加 TURN（coturn，
  自建或 Twilio 托管），成本是带宽——每路通话的每 Mbps 都从 TURN
  服务器的网卡过；
- **无通话记录/铃声**：未接来电不产生消息，无 Web Audio 响铃——
  产品完整性欠账，可用「自动给自己发一条通话摘要消息」补（信令
  服务端不掺和，纯前端逻辑）；
- **单通话并发**：通话中收到新 offer 一律拒。多路通话/呼叫保持是
  产品形态问题，不是技术问题；
- **信令无重试**：answer 丢了 = 一直 connecting。用户侧表现为
  "接通了但没画面"，挂断重拨即可。真实产品在此处加信令 ack 与
  超时重发（对信令通道施加消息级可靠性——注意这是**选项**而非
  必须：Web 呼叫的重拨成本很低）。

## 九、下一步（阶段 9 预告）

1对1 的 P2P 管道有一个硬上限：N 人会议需要 N×(N-1)/2 条管道，
8 人会议 = 每人上传 7 路视频——上行带宽瞬间爆炸。阶段 9 换拓扑：
LiveKit SFU（选择性转发单元）——每人只上传一路，服务器转发给
其余人；屏幕共享成为会议的一个普通 track 而非特殊形态。
信令、鉴权、UI 都在已有骨架上加，服务器侧只加一个 token 签发端点。

## 十、面试题与标准回答

**Q1：为什么信令走你们的 WS、媒体走 P2P？反过来行不行？**

答：不是偏好，是约束推导。信令：低频、小载荷、要可靠送达（丢了
offer 通话就建立不起来）——这正是我们 WS 通道的既有能力（在线判定、
好友门槛、错误反馈全套现成）。媒体：单路 Mbps 级、要求亚秒延迟、
丢帧可容忍——让它过服务器，带宽成本 ×N、延迟多两跳（上行+下行），
而且 TCP/WS 的可靠传输语义反而是毒药（队头阻塞把延迟抖动放大成
卡顿）。反过来做在技术上"能跑"，但在成本与体验两个维度都是下策。
**控制面与数据面分离，各走各的最优路径**——SIP/RTP 三十年前就
把这个结论写进了行业标准。

**Q2：你们的信令为什么不做 ack 和补投？丢了一条 candidate 怎么办？**

答：candidate 的时效以秒计——补投一条过期的候选比丢掉它更有害
（对端会尝试一条已失效的路径）。丢候选的后果很轻：ICE 会继续
枚举其他候选，多数网络里可用路径不止一条；实在全丢了的兜底是
用户挂断重拨，此时整套协商从头再来。**可靠性是要花钱买的**（ack
状态机、离线队列、去重窗口），只该花在收益匹配的地方——消息是
用户发出的每一个字（必须不丢），信令是可重放的协商过程（可丢）。
区分"内容"与"过程"，是设计投递语义的第一刀。

**Q3：远程桌面和视频通话在协议上是两个功能吗？**

答：不是，是**同一根 P2P 管道的两种取流方式**。差别只在呼叫方
第一行：`getUserMedia`（摄像头/麦克风）换 `getDisplayMedia`（屏幕），
以及 offer 里带一个 `media` 标记让接听方知道不必开摄像头。轨道
（MediaStreamTrack）进了管道之后，WebRTC 不关心它是什么——接收端
渲染出来就是"对方的画面"。这个案例的启示：**在正确的抽象层上，
产品形态的多样性不产生协议的多样性**。阶段 9 的会议屏幕共享
（LiveKit 的 share screen）会第三次验证这一点。

**Q4：服务器在一场通话里承担什么？它挂了通话会断吗？**

答：承担三件事：转发信令、裁决 from（来电显示的可信度）、守好友
门槛。P2P 管道建立后，媒体流端到端直连加密（DTLS/SRTP），服务器
一个字节都看不到、也不经手——**服务器挂了，通话继续**，只是无法
再协商新的通话、信令里没发完的 candidate 到不了对端。这个性质
在生产里对应一条运维纪律：信令服务的容量按"通话建立速率"规划，
而不是"并发通话数"——两者差三个数量级。
