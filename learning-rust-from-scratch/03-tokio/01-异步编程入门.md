## 一、为什么需要异步：从线程模型说起

### 逐个连接一个线程（Java 传统模型）

```
100 万连接 × 每线程 1MB 栈 = 1TB 虚拟内存 → 直接爆炸
1 万连接 × 1MB = 10GB → 勉强能跑，但上下文切换开销巨大
```

### 线程池 + 阻塞 IO（Java 常规做法）

```
200 线程的池子：任何时刻最多 200 个连接在处理，其余排队
线程阻塞在 read() 上 = 白白占用一个线程
```

### 事件驱动 + 少量线程（Netty / Tokio / async）

```
几十个线程 + 每个线程管理几万个 IO
线程只在「有活干」时干活，等待期间去处理别的连接
```

> 【Java】Netty 就是第三种；JDK 21 虚拟线程是「用第一种写法获得第三种效果」的运行时魔法。
> Rust async 是第三种的**显式**版本：没有魔法，一切暴露在类型系统里。

### 一个比喻

- 线程阻塞模型：**每人一个服务员**，客人不点菜服务员就干站着（内存爆炸）
- 线程池模型：**200 个服务员**，客人多了就排队（吞吐受限）
- 异步模型：**几个服务员 + 叫号器**，客人点好菜按铃（Waker！），服务员听到铃再去（调度）

## 二、async fn 到底是什么

```rust
async fn fetch(url: &str) -> String { ... }
```

调用它**不执行任何代码**，只生成一个 Future（待执行的计算计划）：

```rust
let f = fetch("http://example.com");   // 什么都没发生！
f.await;                                // 这里才开始执行（或交给调度器）
```

> 这是新手第一坑：**async fn 是惰性的**。
> 调用后不 await 也不 spawn，里面的代码永远不会执行
> （clippy 的 `let_underscore_future` 会提醒你）。

### .await 时发生了什么（先建立直觉，下篇深挖）

1. 执行到当前位置，若数据就绪 → 直接继续（快路径）
2. 未就绪 → 把「我该被怎么唤醒」（Waker）登记给事件源，**当前任务暂停**
3. 线程**不阻塞**，调度器让它去跑别的任务
4. 事件就绪 → Waker 被调用 → 任务回到队列 → 线程空闲时恢复执行

```
同步世界：等待 = 线程睡觉（系统资源被占用）
异步世界：等待 = 任务挂起（只是一段堆上的状态机数据，线程去干别的）
```

## 三、第一个 Tokio 程序

```toml
[dependencies]
tokio = { version = "1", features = ["full"] }
```

```rust
use tokio::time::{sleep, Duration};

#[tokio::main]                    // 宏：把 main 包进 Tokio 运行时
async fn main() {
    // ① 顺序执行：总共 2 秒
    sleep(Duration::from_millis(1000)).await;
    sleep(Duration::from_millis(1000)).await;
    println!("顺序：2 秒过去了");

    // ② 并发执行：总共 1 秒！
    let a = sleep(Duration::from_millis(1000));   // 创建两个 future
    let b = sleep(Duration::from_millis(1000));
    tokio::join!(a, b);                            // 并发等待
    println!("并发：1 秒就够");
}
```

`#[tokio::main]` 展开后（理解它就不怕 main 的魔法了）：

```rust
fn main() {
    tokio::runtime::Builder::new_multi_thread()
        .enable_all()
        .build()
        .unwrap()
        .block_on(async { /* 你的 async main 体 */ })
}
```

> 【Java】`block_on` ≈ Netty 的 `sync()` + 事件循环的合体：
> 把异步世界「锚定」在同步的 main 上。整个进程只有一个 block_on 锚点。

### 异步测试

```rust
#[tokio::test]           // 单线程运行时 + block_on，测试专用
async fn test_echo() {
    let result = do_something().await;
    assert!(result.is_ok());
}
```

## 四、什么时候该用 async（重要判断）

| 场景 | 选择 | 原因 |
|------|------|------|
| 高并发 IO（网络服务、代理、网关） | ✅ async | 每连接一个 task 才撑得起数量级 |
| CPU 密集计算 | ❌ 用普通线程（如 rayon） | async 帮不上 CPU，反而碍事 |
| 少量 IO 的 CLI 工具 | 看情况 | std 线程足够简单直接 |
| 混合型（IO + 偶尔重计算） | async + spawn_blocking | 见第 7 篇 |

> **不要为了异步而异步**。async 有真实税：任务调度开销、代码复杂度、
> 生态锁定（整个依赖树都得是 async 的）。IM 网关 100% 应该 async，
> 一个每天跑一次的脚本完全不必。
