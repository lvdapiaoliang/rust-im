# 06 - 同步原语与共享状态

## 本章目标

掌握 async 世界的锁（tokio Mutex vs std Mutex 的致命区别）、
原子类型、Actix 风格的「消息传递 vs 共享内存」抉择。

## 一、std::sync::Mutex 能在 async 里用吗？

**能，但有一条铁律：不能跨 await 持有。**

```rust
use std::sync::Mutex;

// ❌ 死锁陷阱：guard 跨 await
let data = Mutex::new(State::new());
let guard = data.lock().unwrap();
let result = do_async(&guard.field).await;   // guard 还活着！
// 如果另一个任务也想 lock → 卡住整个 worker 线程（std 锁是阻塞的！）
drop(guard);

// ✅ 正确：锁内不 await，用完立刻还
{
    let mut guard = data.lock().unwrap();
    guard.count += 1;
}   // 出块立即释放
let result = do_async().await;
```

std Mutex 的优势：快（futex）、等待期间不占用堆内存、guard 是 `!Send` 时
也不会被意外跨 await（编译器通过 Send 检查帮你抓一部分）。

## 二、tokio::sync::Mutex：异步锁

```rust
use tokio::sync::Mutex;
let data = Mutex::new(State::new());

// 可以跨 await 持有（竞争时等待是「挂起」而不是阻塞线程）
let mut guard = data.lock().await;
let result = query_db(&guard.params).await;   // OK：等 DB 期间锁还在手
guard.cache.insert(key, result.clone());
drop(guard);
```

代价：比 std 慢（需要跨 await 的簿记）。
**选择原则：能不跨 await 就用 std（配 parking_lot 更快）；
确需跨 await（比如 guard 交给异步方法）才用 tokio 的。**

> 【Java】类比：synchronized（不可中断、阻塞线程）vs StampedLock/数据库行锁。
> rust-im 的经验法则：**任务间通信用 channel（本篇第四节），
> 短临界区保护用 parking_lot::Mutex，跨 await 长临界区才 tokio::sync::Mutex**——
> 三层递减使用频率，大部分代码停在第一层。

### RwLock

```rust
use tokio::sync::RwLock;
let config = RwLock::new(Config::default());

let r = config.read().await;      // 多读并发
let mut w = config.write().await; // 独占写
// 适合：读多写少（如配置、路由表快照）。
// ⚠️ 写者饥饿问题：高读压下写者可能一直排队——极端场景考虑写时复制（ArcSwap）
```

## 三、原子类型：能不用锁就不用

```rust
use std::sync::atomic::{AtomicU64, Ordering};

static MSG_COUNT: AtomicU64 = AtomicU64::new(0);

MSG_COUNT.fetch_add(1, Ordering::Relaxed);      // 计数器：Relaxed 够了
let seq = NEXT_SEQ.fetch_add(1, Ordering::SeqCst); // 序号分配：需要全序
```

Ordering 速记（深水区，够用版）：

| Ordering | 语义 | 典型用途 |
|----------|------|----------|
| `Relaxed` | 只保证本操作原子 | 统计计数 |
| `Acquire` | 读端：其后读写不会重排到本次之前 | 读锁/标志位 |
| `Release` | 写端：其前读写不会重排到本次之后 | 发布数据（先写数据再置标志） |
| `SeqCst` | 全局全序 | 多变量协同、拿不准就用它 |

> 【Java】`AtomicLong`/`volatile` 背后是同一套 happens-before 理论。
> Rust 把内存序暴露出来让你选（性能），Java 默认给了个保守值。
> 【实战】rust-im 的 echo server 连接计数（Relaxed）与阶段 2 的
> seq 分配器就是这两个档位的实例。

## 四、消息传递 vs 共享内存：架构抉择

> 「不要通过共享内存来通信，而要通过通信来共享内存」——Go 的口号，Rust 同样适用。

| | 共享内存（Mutex/Arc） | 消息传递（channel/Actor） |
|---|---|---|
| 心智模型 | 数据有一个家，排队访问 | 数据只有一个主人，用信件交流 |
| 死锁风险 | 有（多锁顺序错误） | 无（无锁等待） |
| 等待/背压 | 锁竞争 | channel 满即背压 |
| 适合 | 简单计数器、读多写少配置 | 有状态的实体（连接、会话、定时器） |

### Actor 模式（rust-im 服务端核心架构）

```rust
/// 「会话管理器」Actor：独占 SessionTable，外界只能发消息
enum Cmd {
    Register { user_id: u64, tx: mpsc::Sender<Msg> },
    Route { to: u64, msg: Msg },
    Unregister { user_id: u64 },
}

async fn session_actor(table: &mut SessionTable, mut rx: mpsc::Receiver<Cmd>) {
    while let Some(cmd) = rx.recv().await {      // 单线程独占 table！
        match cmd {
            Cmd::Register { user_id, tx } => table.insert(user_id, tx),
            Cmd::Route { to, msg } => {
                if let Some(tx) = table.get(&to) {
                    let _ = tx.send(msg).await;   // 背压传导
                }
            }
            Cmd::Unregister { user_id } => { table.remove(&user_id); }
        }
    }
}
// 没有 Mutex！table 的唯一主人在这个 actor 里，零锁竞争。
```

> 【实战】rust-im 阶段 3 网关：每连接一个 task（连接 Actor）+
// 会话路由 Actor + 扇出 worker。锁只出现在压测计数器上。
> 【Java】这就是 Erlang/Akka 的 Actor；Java 21 虚拟线程 + 队列可以近似模拟，
> Rust 的所有权让「table 只有一个主人」从纪律变成编译期事实。

## 五、OnceCell/Lazy：异步初始化

```rust
use tokio::sync::OnceCell;

static DB_POOL: OnceCell<Pool> = OnceCell::const_new();

// 多个任务并发调用，只有第一个执行初始化，其余等待复用
let pool = DB_POOL.get_or_init(|| async { Pool::connect().await }).await;

// 同步版：
use std::sync::OnceLock;
static CONFIG: OnceLock<Config> = OnceLock::new();
CONFIG.get_or_init(|| load_config());   // 【Java】双检锁单例的免锁实现
```

> 【Java】`OnceLock` 就是 `volatile` 双检锁单例的标准化，
> 且**不可能**写出错误的 double-checked locking——Java 那个著名坑被类型系统消灭了。
