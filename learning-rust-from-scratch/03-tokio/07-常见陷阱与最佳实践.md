# 07 - 常见陷阱与最佳实践（Tokio 毕业篇）

## 本章目标

把前六篇的知识收束成一张「实战检查清单」。
本文每一节都对应一类真实事故——rust-im 开发过程中全部踩过或预防过。

## 陷阱 1：在 async 里调用阻塞代码

```rust
// ❌ 事故现场（三连）
std::thread::sleep(Duration::from_secs(1));     // 阻塞 worker
std::fs::read_to_string("f.txt")?;               // 同步文件 IO
let result = std_db_query(&conn)?;               // 同步 DB 驱动
// 后果：同 worker 所有任务冻结，P99 延迟出现神秘尖刺

// ✅ 修复
tokio::time::sleep(Duration::from_secs(1)).await;                    // ①
tokio::fs::read_to_string("f.txt").await?;                           // ②
tokio::task::spawn_blocking(move || std_db_query(&conn)).await??;    // ③
```

**排查手段**：tokio-console（实时观察任务状态）；
`tokio::runtime::Builder::start_paused` + 测试；
压测时看 P99 毛刺与 worker 饥饿 metrics。

## 陷阱 2：忘了 await / spawn

```rust
async fn send(msg: Msg) { ... }

// ❌ future 未执行，编译器只给警告（future 不 send 之类的 lint）
fn process() {
    send(msg);              // 调用了 async fn 却没 await！
}

// ✅ Rust 2024 已把这种情况升级为编译错误；老代码注意 #[must_use]
```

## 陷阱 3：block_on 嵌套 panic

```rust
#[tokio::main]
async fn main() {
    let rt = tokio::runtime::Runtime::new().unwrap();
    rt.block_on(other_async());    // ❌ panic: cannot block the current thread
    // 原因：当前线程已是 runtime 的 worker，不能在里面再 block_on
}

// ✅ 修复：用 Handle::current().block_on()（同 runtime 的句柄）
// 或者本来就该 .await / spawn
```

## 陷阱 4：Send 错误的未来状态机

```rust
// ❌ 常见报错：future cannot be sent between threads safely
async fn handler(rc: std::rc::Rc<Config>) {   // Rc 是 !Send
    let cfg = rc.clone();
    tokio::spawn(async move {                  // spawn 要求 Send
        use_cfg(&cfg).await;                   // 跨 await 持有 !Send → 整个 future !Send
    });
}

// ✅ 修复：Rc → Arc（或提前在 await 前用完）
```

> 这是 Rust async 报错最劝退的一个。读法：顺着错误信息里的
> 「note: future is not `Send` as this value is used across an await」
> 找到具体变量——报错定位是准的，只是信息长。

## 陷阱 5：取消安全（第 5 篇的复习）

select! 分支优先用取消安全的 API；`read`/`write_all` 必须用 `pin! + &mut` 复用进度。
**口诀：写 select 前，先问每个分支「如果这里被取消，丢了什么？」**

## 陷阱 6：channel 用错语义

```rust
// ❌ 用 broadcast 传「每条都重要」的消息：慢消费者 Lagged 丢消息！
// ✅ 重要消息用 mpsc（有背压）；broadcast 只用于可丢弃的事件（如在线状态）
// ❌ 用 watch 传消息：新消费者只能看到最新一条
// ✅ watch 只传「状态快照」（如配置、当前服务器时间）
```

## 陷阱 7：任务泄漏

```rust
// ❌ spawn 的任务永远不结束（循环里忘了退出条件 / 对端断了没感知）
tokio::spawn(async {
    loop { do_work().await; }              // 永动机 = 泄漏
});

// ✅ 每个长任务必须有明确的终止设计：
// - channel 关闭（rx.recv() 返回 None）
// - CancellationToken
// - 资源 drop（RAII：连接断了任务自然结束）
```

**观测**：`tokio::spawn` 返回的 JoinHandle 不 await 也不 drop 的话，
任务可能静默 panic——加监控或统一走「任务管理器」封装。

## 陷阱 8：持有锁跨 await 造成串行化

```rust
// ❌ 看似无害：所有请求排队（锁跨 await = 吞吐悬崖）
let mut sessions = state.lock().await;
let user = db.find(id).await;         // 锁还在手！
sessions.insert(id, user);

// ✅ 先取数据，最小化锁区间
let user = db.find(id).await;
state.lock().await.insert(id, user);
```

## 最佳实践清单（写码前扫一眼）

**结构**：

1. main 只做：构建运行时 → block_on 入口 → 优雅停机
2. 每连接/每会话一个 task，task 之间只靠 channel 通信（Actor 化）
3. 共享只读数据 `Arc<T>`；共享可变数据先问「能不能变成消息传递」
4. 优雅停机三件套：signal 监听 + CancellationToken + drain（等在途任务完成）

**IO**：

5. 读循环 + `read_buf`（BytesMut，自动扩容，零拷贝友好）
6. 所有网络等待包 timeout；心跳间隔 > 客户端超时（先 ping 后断）
7. 写路径独立 task + mpsc 有界 channel（读写分离 + 内建背压）

**正确性**：

8. select 分支逐个检查取消安全性
9. 长任务必须有终止路径；错误统一 thiserror/anyhow 分层（→ 基础篇 05）
10. 测试用 `#[tokio::test]` + `start_paused`（虚拟时钟，时间快进测超时）

```rust
#[tokio::test(start_paused = true)]     // 时间虚拟化：sleep(1h) 瞬间完成
async fn test_heartbeat_timeout() {
    let start = std::time::Instant::now();
    tokio::time::sleep(Duration::from_secs(3600)).await;   // 秒过
    assert!(start.elapsed() >= Duration::from_secs(3600)); // 逻辑上过了 1 小时
}
```

## 性能清单（进阶，配合阶段 5）

11. 热路径避免 per-message 堆分配（Bytes/对象池/SmallVec）
12. 批量化：channel 批量收（`recv_many`）、写合并（writev / `write_all_buf`）
13. 锁粒度：分片锁（DashMap）替代全局锁；计数用原子不用锁
14. 大量小任务时关注 spawn 成本：考虑 `LocalSet`（单线程批量 spawn 免 Send）
15. profile 优先：cargo flamegraph 找热点，再谈优化
