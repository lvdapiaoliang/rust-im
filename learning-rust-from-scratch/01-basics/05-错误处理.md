# 05 - 错误处理：panic、Result 与 `?`

## 本章目标

掌握 Rust「错误即类型」的哲学：panic 与 Result 的分界、`?` 运算符、
错误类型设计（thiserror/anyhow 分层）。

## 一、两层错误模型

| | panic | Result |
|---|-------|--------|
| 语义 | 不可恢复的 bug（不变量被破坏） | 可预期的失败（文件不存在、网络断开） |
| 【Java】 | `Error` / 未捕获 RuntimeException | `IOException` 等 checked 异常 |
| 传播 | 栈展开，线程终止（可 catch_unwind 但别依赖） | 显式传播，类型系统跟踪 |
| 使用 | 测试断言、索引越界、`unwrap` 失败 | 一切业务失败 |

> 【Java】核心差异：Java 用异常「跳出」调用栈（控制流魔法）；
> Rust 的 Result 是**普通值**，必须有人处理——错误路径和成功路径一样，
> 都在函数签名里白纸黑字写着，没有隐藏控制流。

```rust
// panic 场景示例：
// let v = vec![1, 2, 3];
// v[10];                       // 越界 panic（生产代码用 v.get(10) 拿 Option）
// "abc".parse::<i32>().unwrap(); // unwrap 遇 Err 即 panic

// Result 场景示例：
use std::fs::File;
let f = File::open("config.toml");   // 返回 Result<File, io::Error>
```

## 二、Result 与 `?`

```rust
enum Result<T, E> { Ok(T), Err(E) }   // 标准库定义

fn read_config() -> Result<String, std::io::Error> {
    // 写法演进（同一逻辑）：

    // ① 初学者写法：match 显式处理
    let f = match File::open("config.toml") {
        Ok(f) => f,
        Err(e) => return Err(e),
    };

    // ② ? 运算符：完全等价上面 5 行！
    let mut f = File::open("config.toml")?;
    use std::io::Read;
    let mut s = String::new();
    f.read_to_string(&mut s)?;
    Ok(s)
    // ③ 更简：std::fs::read_to_string("config.toml")?
}
```

`?` 的行为：`Ok(v)` → 解包继续；`Err(e)` → **提前返回 `Err(错误转换后的 e)`**。
「错误转换」指它会尝试 `From::from`，所以函数的错误类型和内部错误的类型不一致时，
只要实现了 `From` 就能自动转换——这是 Rust 错误传播的核心机关。

`?` 也能用于 Option（None 提前返回 None）。

### 在 main 里收尾

```rust
fn main() -> Result<(), Box<dyn std::error::Error>> {
    let cfg = read_config()?;
    println!("{cfg}");
    Ok(())   // 出错时 main 返回 Err，程序以非零码退出并打印错误
}
```

## 三、错误类型设计：thiserror（库）与 anyhow（应用）

业界标准分层：

```rust
// 库 / SDK / 可被别人依赖的代码：用 thiserror 定义精确错误枚举
use thiserror::Error;

#[derive(Debug, Error)]
pub enum TransportError {
    #[error("连接失败：{addr}")]
    Connect { addr: String, #[source] source: std::io::Error },
    #[error("心跳超时：{elapsed_ms}ms 无响应")]
    HeartbeatTimeout { elapsed_ms: u64 },
    #[error("协议错误：{0}")]
    Protocol(#[from] crate::protocol::Error),   // #[from] 自动实现 From
}

// 应用 / bin / main：用 anyhow 不关心错误具体类型，只管传播和打印
fn main() -> anyhow::Result<()> {
    let conn = connect("127.0.0.1:8080").context("初始化 IM 连接失败")?;  // 附加上下文
    Ok(())
}
```

判断口诀：**你要暴露 API 给外部 → thiserror 精确类型；
你只是终端消费者 → anyhow 简单粗暴。**

> 【实战】rust-im 全 workspace 就是这个分层：`im-protocol`/`im-transport` 用 thiserror
> （它们是库，调用方要 match 具体错误做重连/限流决策）；
> `im-server`/`im-client` 入口用 anyhow。
> 【Java】类比：库抛具体异常类（IOException），应用层统一 catch Exception 打日志。

## 四、自定义错误转换实战

```rust
use std::num::ParseIntError;

#[derive(Debug, thiserror::Error)]
enum ConfigError {
    #[error("端口必须是数字")]
    BadPort(#[from] ParseIntError),        // ? 自动转换的关键
}

fn parse_port(s: &str) -> Result<u16, ConfigError> {
    let n: u16 = s.parse()?;               // ParseIntError --From--> ConfigError
    Ok(n)
}
```

## 五、什么时候可以 unwrap

- 单元测试（失败即测试失败，正是想要的）
- 原型/演示代码
- 能**证明**不可能失败的场景（如 `"GET".parse::<&str>()`）——即使这样，社区仍推荐 `expect("理由")` 代替 unwrap，崩溃信息里能看到你的理由
